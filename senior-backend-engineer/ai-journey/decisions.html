Phase 1 · Brainstorming

Q1 · Must the assignee of a work item be an existing user?

Agreed with AI
Question
AI

Three options: (A) check synchronously through a public Users contract, (B) eventual consistency through a UserCreated event and a local copy, (C) no check. Recommended A, with B in the README as the evolution path.

Answer
Candidate
I think A, but which architecture we're following? clean architecture or vertical slice? remember simple is the best, easy to read, easy to maintenance
Outcome
A. "Simple is the best" became the guiding principle for every later choice.

Q2 · Clean Architecture or vertical slices?

Agreed with AI
Question
AI

Recommended vertical slices inside each module, with a Domain/ folder for DDD and a Users.Contracts project as the only cross-module reference. Rejected Clean Architecture because it would mean about 8 projects for 4 endpoints.

Answer
Candidate
I think this structure is good to go
Outcome
Vertical slices per module.

Q3 · Which CQRS library?

Candidate overrode AI
Question
AI

Recommended small hand-written ICommand/IQuery interfaces with no library. Alternatives: the FastEndpoints command bus ("queries become commands, so the split blurs"), MediatR (went commercial), and Mediator (source-generated).

Answer
Candidate
as Mediatr goes commercial I think I will go with fastendpoint. as CQRS pattern is how we control, use it, not just because its name. the implementation class can be name *Query while implemting the ICommand interface. I think it does not matter
Outcome
FastEndpoints command bus. The split is kept by naming (*Command / *Query) and by how the classes are used, not by interface type.

Q7 · Where is validation, and what about concurrency?

Candidate corrected AI
Question
AI

Presented the request flow and module wiring (Section 2) and asked for approval.

Answer
Candidate
it looks right, but I just want to follow up with some questions, there is the validation? also we should handle the concurrency issue with adding/updating data.
AI

Explained the three validation layers. Admitted that the username check followed by a separate add was a race: two requests at once could both pass. Changed it to an atomic TryAddAsync.

Outcome
The candidate's question exposed a real race in the AI's design. Username uniqueness is now enforced atomically.

Q8 · Build update concurrency now?

Agreed with AI
Question
AI

No update use cases exist. Recommended documenting optimistic concurrency (a version number, then ETag and If-Match) rather than building it.

Answer
Candidate
no, the requirement does not mention it. but should we handle idempotency, when somehow user double click? and create 2 same workitem?
Outcome
Documented in the README, not built. The candidate raised idempotency as a new topic (Q9).

Q9 · Should double submissions be prevented?

Candidate overrode AI
Question
AI

Recommended documenting an Idempotency-Key header rather than building it, for the same reason as Q8: the brief doesn't ask for it.

Answer
Candidate
how about idempotency check for a certain window? like 10s? because there is very low chance of a human create 2 identical workitem on purpose in 5-10s.
AI

Read this as deduplicating by content (same name and assignee) and argued against it: it brings the race back, and the rule would sit in the wrong layer.

Candidate
no I mean we still need idempotency key require from the client and use that key for 10s window. how that sound?
AI

Designed it: the key is required on both POSTs, the window is 10 seconds and configurable, the original response is replayed, keys are reserved atomically, and it all lives in the Host.

Outcome
Built. The candidate overrode "document only" and supplied the design (client key plus a short server-side window), which avoids the problems the AI raised.

Q10 · Does a retry use a new key?

Candidate corrected AI
Question
AI

Described the trade-off of a 10-second window in a way that read as if a retry would use a new key.

Answer
Candidate
oh, good to know that trade off. but retrying should not change the idempotency key, I think. other stuffs are good for me.
AI

Agreed: retries reuse the key, and the real limit is that the server forgets keys after 10 seconds. Also corrected its own earlier claim that the store stays small. Most keys are never reused, so expired keys are now removed on every reservation.

Outcome
Wording fixed, plus an AI self-correction: expired keys are purged so memory stays bounded.

Phase 2 · Written spec review

Q12 · Why make module types internal?

Agreed with AI
Question
Candidate
hrm, I don't think we should use internal here. as we only have 1 project. internal should be same as public. Ah I see now, we need it internal as Test project should only ref to the Contracts, right?
Answer
AI

Not quite. The project references are what keep the two modules apart. internal protects against the projects that do reference a module (the Host and tests), so Program.cs can't build repositories or aggregates directly. It's also the C# default, so it costs nothing.

Candidate
agree.
Outcome
Kept internal; the reasoning was added to the spec.

Q15 · Are value objects overcomplicating this?

Candidate pushed back
Question
Candidate
Tell me why we need value object here? any tradeoff, why not just POCO? looks like we over complicated? if so explain why?
Answer
AI

The brief explicitly grades value objects and invariants. Offered (A) value objects everywhere, including strongly-typed IDs, or (B) value objects only where a rule lives, with plain Guid IDs. Recommended B.

Candidate
well I think that's a good catch for option B, by let says how this is adaptable for different database? like sql or no sql with ef core? like I kinda cannot imagine what it looks like for sql database with ef core. what columns looks like?
AI

Showed the EF Core mapping: a value object becomes one column through HasConversion, with a unique index on Username and no foreign key between the module schemas.

Outcome
Option B: only Username and WorkItemName are value objects, and four types were dropped. A "persistence portability" section was added to the spec.

Q16 · "DomainException" or "ApiException"?

Agreed with AI
Question
Candidate
I prefer the name ApiException. there is any meaning of using the name DomainException?
Answer
AI

The name says where the rule broke, not who handles it. The domain shouldn't describe itself in API terms.

Candidate
agree, then for what exception comming from other places/ business it should be different name, you says?
AI

Yes, each exception is named for the kind of failure: DomainException (400), ConflictException (409), BusinessRuleViolationException (422).

Outcome
Kept the three names; the naming rule was added to the spec.
