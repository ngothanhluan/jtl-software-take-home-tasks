The prompts that shaped the build

The candidate's prompts that changed the outcome, in order, quoted exactly as typed (typos included). Each has one line on what it caused. The full context for each one is in the decision log and transcript.md.

Date 2026-10-08 Also decisions Also toolchain Also judgment

01Opening the session

Candidate
/superpowers:brainstorming this repo is a home work test from an interview for role senior backend engineer. Please read the readme from the root repo and the senior back end engineer folder then help me to complete the task. if there is any question, please ask. if there is anything unclear, please ask.

Caused: an ask-first process. The AI asked one design question at a time before writing any spec or code, and kept asking whenever something was unclear.

02The guiding principle

Candidate
I think A, but which architecture we're following? clean architecture or vertical slice? remember simple is the best, easy to read, easy to maintenance

Caused: vertical slices per module instead of Clean Architecture layers (Q2). Every later choice was checked against "simple is the best".

03Choosing the CQRS mechanism

Candidate
as Mediatr goes commercial I think I will go with fastendpoint. as CQRS pattern is how we control, use it, not just because its name. the implementation class can be name *Query while implemting the ICommand interface. I think it does not matter

Caused: the AI's hand-written interfaces were dropped for the FastEndpoints command bus (Q3). The command/query split is kept by naming and use.

04Specific error messages

Candidate
agree on option1. Also just want to push back the error handling. is that error return with specific error message? I expect that it would be something "Username is already existed" when checking username uniqueness

Caused: every error carries a specific message in the problem details detail field (Q6). The test plan then fixed the exact wording.

05Validation and concurrency

Candidate
it looks right, but I just want to follow up with some questions, there is the validation? also we should handle the concurrency issue with adding/updating data.

Caused: the AI found a race in its own design: a username check followed by a separate add. Uniqueness became one atomic TryAddAsync (Q7), now tested by TC-U05.

06Double clicks and the idempotency window

Candidate
no, the requirement does not mention it. but should we handle idempotency, when somehow user double click? and create 2 same workitem?
Candidate
no I mean we still need idempotency key require from the client and use that key for 10s window. how that sound?
Candidate
oh, good to know that trade off. but retrying should not change the idempotency key, I think. other stuffs are good for me.

Caused: the AI wanted to only document idempotency; the candidate had it built (Q9). The design is a required Idempotency-Key with a 10-second window. The candidate also corrected the AI's wording about retries (Q10).

Caused: the project was renamed to WorkTracker.Shared. Value objects were cut to Username and WorkItemName. The decision log became a raw log quoting the candidate. A test plan approved before code became the gate (Q12–Q19).

09Implementation

Candidate
let follow the implementation plan and start building it.
Candidate
ah see, I already turned that off, please try one more time

Caused: the AI built the ten tasks itself, test-first, one commit per task. Windows Smart App Control blocked the unsigned test DLLs part-way through. The candidate turned it off, and the build continued natively.

10Review and UAT

Candidate
let talking about those minor points that you've raised. please bring it up and see if it worth to fix or not or it's just something might never happen.
Candidate
1. well I think you're right, I'd like to beautify this. please do
2. absolutely right, I think we only need to log unexpected error.

Caused: the AI weighed each reviewer point by likelihood, visible effect and cost of fixing, rather than by its severity label. The candidate chose two fixes: error responses with one shape and plain messages, and logs that only record unexpected failures. Both were made test-first. See Q26.

11Fewer tests

Candidate
2. I think the requirement is quite right, and the Ai problem is writing too much tests. which I think sometime there are some tests not necessary.

Caused: the AI re-read the brief's "No exhaustive test coverage" line and cut the suite from 52 cases to 32, one or two per design point. See Q27.

12Checking against the brief

Candidate
did you evaluate the whole project with [the six "What we evaluate" criteria] ultracode ?

Caused: a 13-agent evaluation against the brief's own criteria, with a skeptic refuting each evaluator. All six came back Strong; the candidate accepted four of the five text fixes and turned UAT-10 into an exact check. See Q28.
