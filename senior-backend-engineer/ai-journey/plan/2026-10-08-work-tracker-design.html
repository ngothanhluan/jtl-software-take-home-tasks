01Goal

A small .NET 8 service, organized as a modular monolith, using FastEndpoints, CQRS and DDD, with two modules:

  • Users: create a user by username; get a user by ID.
  • WorkItems: create a work item with a name and an assignee (user ID); list work items by assignee.

The brief grades module boundaries, a deliberate domain model, a clean command/query split, thin endpoints, testability, clarity, and the AI journey. Time box 2–4 hours, with no gold-plating.

Guiding principle (set by the candidate)

Simple, easy to read, easy to maintain. Build what the brief asks for. Document what it doesn't ask for instead of building it, unless we chose to build it deliberately (see §08).

02Architecture

Vertical slices inside each module, with the domain model in its own folder. We chose this over Clean Architecture's project-per-layer, which would mean about 8 projects for 4 endpoints and reading one use case across 4 projects.

Boundary rules

  • The boundary between modules is the project-reference graph. WorkItems has no reference to Users, so it can't touch Users' types at all.
  • Everything inside a module project is internal (the C# default; we just never write public). This guards the projects that do reference a module, namely the Host and the tests: Program.cs can't construct a repository or an aggregate directly. A module's public surface is exactly its Add<Module>Module(this IServiceCollection) extension and, for Users, its Contracts project.
  • Modules never share domain types. Only primitives (Guid, string) cross a boundary.
  • Each module owns its own data store, and no module can see another's.
  • Shared holds exception types only, never business concepts.
  • Each module declares InternalsVisibleTo for its own test project.

03Domain model

We use value objects only where a rule lives. IDs are plain Guid; a strongly-typed ID per aggregate was judged too much ceremony for two aggregates. Aggregates have private constructors and factory methods, so they can never be in an invalid state.

Users

  • Username: a value object. It's trimmed and required, 3–32 characters, and allows only letters, digits, ., _ and -. Equality ignores case. A broken rule throws DomainException with a specific message, such as "Username is required." or "Username must be between 3 and 32 characters.".
  • User: the aggregate root. It has a private constructor and User.Create(Username), and exposes Guid Id and Username Username. There are no setters and no methods that change it.
  • IUserRepository (in Domain/):
    • Task<bool> TryAddAsync(User user, CancellationToken ct) is atomic. It returns false if the username is already taken (ignoring case).
    • Task<User?> GetByIdAsync(Guid id, CancellationToken ct)
    • Task<bool> ExistsAsync(Guid id, CancellationToken ct)

WorkItems

  • WorkItemName: a value object. It's trimmed and required, 1–200 characters. A broken rule throws DomainException.
  • WorkItem: the aggregate root, created with WorkItem.Create(WorkItemName name, Guid assigneeId). It throws DomainException("Assignee id is required.") for Guid.Empty. It exposes Guid Id, WorkItemName Name and Guid AssigneeId. There's no status, due date and so on, because nothing asks for them.
  • IWorkItemRepository (in Domain/):
    • Task AddAsync(WorkItem item, CancellationToken ct)
    • Task<IReadOnlyList<WorkItem>> GetByAssigneeAsync(Guid assigneeId, CancellationToken ct)

Cross-module contract

// WorkTracker.Users.Contracts
public interface IUsersApi
{
    Task<bool> UserExistsAsync(Guid userId, CancellationToken ct);
}

An internal UsersApi class in the Users module implements it, using IUserRepository, and AddUsersModule() registers it. WorkItems checks assignees through it synchronously.

Persistence portability (documented, not built)

Changing the data store doesn't change the domain model. Only Infrastructure/ changes.

StoreHow it maps
SQL via EF CoreOne DbContext and one schema per module (users.Users, workitems.WorkItems). Username maps to a single nvarchar(32) column through HasConversion(u => u.Value, s => new Username(s)), with a unique index that ignores case. TryAddAsync catches the unique-violation DbUpdateException and returns false. EF Core copes with the private constructor and private setters. There's no foreign key from WorkItems.AssigneeId to Users.Id, because that would couple the modules at the database level.
IDsGuid suits in-memory storage because the app generates it, with no round trip to a database. With SQL the candidate prefers int/long identity columns (or sequential UUIDv7), and the repository would then return the generated ID.
Document storeOne document per aggregate, with the value object stored as a plain field.

  • Both POSTs require an Idempotency-Key header (§08).
  • POST /work-items returns 201 without a Location header. There's no get-single-work-item endpoint, and we don't add one.

  • Each module owns its own URL space (/users, /work-items).
  • Swagger UI comes from FastEndpoints.Swagger. requests.http covers every call and every error case.

05Request flow (CQRS)

CQRS uses FastEndpoints' built-in command bus. Commands and queries both implement ICommand<TResult>. Three things keep them apart:

  • their names (*Command or *Query);
  • the rule that query handlers never change state;
  • the rule that a command and a query never share a handler.

We rejected MediatR because it went commercial. The accepted cost is that handlers depend on FastEndpoints, which the modules already reference for their endpoints.

Each use case gets one feature folder. For example, Features/CreateWorkItem/ holds CreateWorkItemEndpoint.cs, CreateWorkItemCommand.cs, CreateWorkItemHandler.cs and CreateWorkItemRequest.cs. The response DTOs (UserResponse, WorkItemResponse) are shared within their module.

HTTP POST /work-items
 └─ CreateWorkItemEndpoint            maps Request → Command (one line), no logic
     └─ command.ExecuteAsync(ct)       FastEndpoints command bus
         └─ CreateWorkItemHandler
             ├─ new WorkItemName(cmd.Name)            → DomainException (400)
             ├─ usersApi.UserExistsAsync(...)         → false: BusinessRuleViolationException (422)
             ├─ WorkItem.Create(name, cmd.AssigneeId) → DomainException if empty (400)
             ├─ repository.AddAsync(workItem)
             └─ return WorkItemResponse (DTO)
     └─ Send.ResponseAsync(response, 201)

Rules

  • Endpoints map the request to a command or query, execute it, and send the response. Nothing else.
  • Handlers run the use case: they build value objects, call the aggregate and save. They return DTOs, never domain objects.
  • Query handlers only read and map. They never change state.

Validation: each rule lives in exactly one place

LayerChecksResult
FastEndpoints bindingmalformed JSON, IDs that aren't GUIDs400
Value objects / aggregate factoryrules about a single object (required, length, characters, empty assignee)400
Handlersrules that need data (username taken, assignee exists)409 / 422

We don't use FastEndpoints validators, because they would repeat the domain rules.

06Error handling

Exceptions for broken rules, null for not found. Each exception is named after the kind of failure, not the layer that handles it. Shared defines them:

ExceptionThrown fromMeaningHTTP
DomainExceptionDomain/a rule of a single object is broken400
ConflictExceptionhandlersthe thing already exists (username taken)409
BusinessRuleViolationExceptionhandlersa rule involving other data fails (unknown assignee)422
  • Every exception carries a specific, readable message, written where the rule lives. Examples: "Username 'alice' already exists.", "User '3f2a…' does not exist."
  • One IExceptionHandler in the Host turns them into ProblemDetails (RFC 9457) and puts the message in detail. Any other exception becomes a generic 500 that exposes no internal details.
  • Query handlers return null when nothing is found, and the endpoint sends a 404 with "User '{id}' was not found."
  • FastEndpoints is set to Errors.UseProblemDetails(), so its own binding errors come back in the same format.
HTTP/1.1 409 Conflict
{
  "type": "https://tools.ietf.org/html/rfc9110#section-15.5.10",
  "title": "Conflict",
  "status": 409,
  "detail": "Username 'alice' already exists."
}

07Concurrency

  • Username uniqueness is enforced atomically. InMemoryUserRepository keeps a second ConcurrentDictionary keyed by the lower-cased username, and TryAdd succeeds for exactly one caller. When TryAddAsync returns false, the handler throws ConflictException. There's no separate check before the add. In production, the equivalent is a unique index plus catching the violation.
  • Work items have no uniqueness rule, so adding them concurrently is already safe.
  • Aggregates never change after creation, so readers can't see half-changed data.
Update concurrency: documented, not built

There are no update use cases yet. When there are: a Version on each aggregate, compare-and-swap in the repository, and a 409 on mismatch. Over HTTP that becomes an ETag and If-Match header, answered with 412.

08Idempotency Deliberate addition

This protects both POST endpoints against double submission, such as a double click.

  • The client sends an Idempotency-Key header and reuses the same key when it retries.
  • The server remembers each key for a configurable window (Idempotency:WindowSeconds, default 10).
SituationResponse
Header missing or empty400 "Idempotency-Key header is required."
First request with the keyhandled normally; the 2xx response (status, body, Location) is stored
Same key + same request within the windowstored response replayed with header Idempotent-Replayed: true; nothing created
Same key, first request still in progress409 "A request with this Idempotency-Key is already being processed."
Same key, different endpoint or body422 "Idempotency-Key was already used with a different request."
First request failed (4xx/5xx)key released, so the client can retry with the same key
After the windowkey forgotten; the request is handled as new

Design

  • It lives entirely in WorkTracker.Host/Idempotency/. It's an HTTP concern, so the modules and the domain don't know it exists.
  • IdempotencyPreProcessor (IGlobalPreProcessor) and IdempotencyPostProcessor (IGlobalPostProcessor) are attached to POST endpoints only, through c.Endpoints.Configurator.
  • A request is identified by its endpoint route plus a SHA-256 hash of the request DTO serialized as JSON.
  • IdempotencyStore is a singleton built on a ConcurrentDictionary keyed by the idempotency key:
    • Reserving a key is atomic (TryAdd, or TryUpdate over an expired entry).
    • Each reservation also removes expired entries, so memory holds only the keys from the current window.
    • Time comes from an injected TimeProvider.
  • If the handler throws, the post-processor releases the key and lets the exception go on to the ProblemDetails handler.
Known trade-off

A 10-second window covers double clicks, but not slow automatic retries. A client that times out at 30 seconds and then retries with the same key gets a duplicate. The window is configurable, and payment APIs such as Stripe keep keys for 24 hours. In production the equivalent is Redis SET key NX EX <window>, which also works across several instances.

09Testing

  • xUnit + Shouldly 4.3.0 (BSD-3-Clause). We avoided FluentAssertions because it went commercial. We considered AwesomeAssertions too, but it keeps the FluentAssertions namespace, which would mislead readers.
  • Test plan first. ai-journey/plan/test-plan.html lists numbered cases (TC-U01, …) in Given/When/Then form, and the candidate approves it before any code is written. Each test method name includes its case ID, so every test traces back to the plan.
  • TDD while implementing: write the test, watch it fail, make it pass.
  • Manual UAT is the final gate: a checklist at the end of requests.http that the candidate runs against the live service.
